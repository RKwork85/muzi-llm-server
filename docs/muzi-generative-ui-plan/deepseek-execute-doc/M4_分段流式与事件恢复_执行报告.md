# M4 · 分段流式与事件恢复 — 执行报告

状态：**CODE_PASS**（SSE 分段 + 事件序列 + outbox 已落地；断线重连的浏览器端到端未实测）

## 1. 阶段目标

实现文本增量、组件独立就绪、事件重放和断线恢复，不依赖解析半截 JSON。

## 2. 现状审计结论

- **模型 Token 流与客户端事件流解耦**：`PlanningDecisionEngine.propose_stream` 逐段 yield `delta`，组件在完整 JSON 校验通过后才作为 `interaction` 事件下发，**不在半截 JSON 阶段展示组件**。
- **分段事件协议**：`SqlPlanningStore.process_message_stream` 按序产出 `delta → interaction_pending → plan → interaction → done`。
- **事件持久化**：`plan_events`（`sequence` 单调递增，`uq_plan_events_sequence`）+ `plan_event_outbox`（事务性投递）。
- **恢复接口**：`GET /plans/{id}/events?after=N`、`GET /conversations/{id}/events?after=N` 按序号增量恢复。

## 3. 关键交付物

### 3.1 事件模型（`contracts.py::PlanningEventType`）

```text
chat.run.started / chat.delta / chat.tool / chat.status / chat.done / chat.error / chat.cancelled
plan.created / plan.updated / plan.approved / plan.paused / plan.resumed / plan.cancelled / plan.completed
interaction.ready / interaction.required / interaction.submitted / interaction.skipped
conversation.mode_changed / handoff.created / run.started / run.progress / run.completed / run.failed / run.cancelled
```

### 3.2 流式组装边界（`runtime.py::propose_stream`）

- 用正则 `_extract_response_preview` 从**未完成 JSON 流**中提取 `response` 字段文本做打字机预览。
- 用 `_ACTION_FIELD` 提前识别 `ask_user`/`request_approval`，发 `interaction_pending` 让前端先出「预告卡」占位。
- 组件 `block.ready` 语义等价于「完整 JSON 通过 `DecisionProposal.model_validate` 后，`SqlPlanningStore.apply_proposal` 落库并 emit `interaction.required`」。

### 3.3 序列化与 Outbox（`sql_store.py::_emit`）

- `sequence = max(sequence)+1`，`event_id` 唯一；`_emit` 在同一事务内写 `plan_events` + `plan_event_outbox`。
- `_emit_conversation` 支持无 plan 的会话级事件（如 `mode_changed`）。

## 4. 验收标准逐条核查

| 验收项 | 结果 | 证据 |
|---|---|---|
| 断线重连后 UI 与服务端快照一致 | 满足（后端能力） | `events_after`/`conversation_events_after` + `plan_revisions` 快照；前端 `listPlanEvents` 已接但无 e2e 用例 |
| 重复/乱序事件不会重复组件或覆盖新状态 | 满足（后端） | `sequence` 单调 + `uq_plan_events_sequence`；交互提交有幂等键 |
| block.ready 前不展示非法未完成组件 | 满足 | 组件只在完整校验后 emit |
| 工具结果延迟时文本仍可持续流式展示 | 满足 | `delta` 独立于组件流；plan 模式无阻塞工具调用 |
| 多实例部署事件可恢复 | 满足（设计） | `plan_event_outbox` 事务性投递；多实例读取同一事件表 |

## 6. 差距与风险

- **前端 Reducer / 快照恢复未独立成模块**：`docs` 建议 `eventReducer.ts`/`snapshotRecovery.ts`，实际前端通过 `ChatSession.vue` 内联 `listPlanEvents` 与 `getPlan` 恢复，未抽象为独立 reducer（功能等价，可维护性略弱）。
- **Last-Event-ID / cursor 断点续传**：接口用 `after=sequence` 实现，但前端 SSE 断线后是否自动携带 cursor 续传未在浏览器端验证（BLOCKED）。
- **outbox 的投递 worker 未实现**：`plan_event_outbox` 表已建，但未见独立的投递/重试 worker（当前 SSE 直推，outbox 作为审计与重放源）。若未来要保证「至少一次投递」需补 worker。

# M3 · 模型自主选择 UI 组件 — 执行报告

状态：**CODE_PASS**（决策引擎 + 结构化提案 + 校验修复已落地；评测集本轮补齐 44 例，跑分器未建）

## 1. 阶段目标

让模型在受控能力目录内决定是否需要 UI、选择组件及布局，并在失败时退回文本。

## 2. 现状审计结论

模型自主选择组件的能力已通过 `PlanningDecisionEngine` 完整落地：

- **决策边界**：模型只表达意图与选择，后端负责授权、风险与执行。模型提案 `DecisionProposal` 是「不可信输入」，服务端校验后落地。
- **结构化生成**：`response_format={"type":"json_object"}` 强制结构化输出，`DecisionProposal` 契约严格校验，禁止模型直接执行代码。
- **文本优先**：提示词 `STEP 0` 明确「非规划类消息（寒暄/问答/致谢）一律 `respond`，不生成卡片」，实现文本优先。
- **组件选择策略**：把未知事实分为「硬约束/软偏好/琐事」三类——硬约束必须问（单选或表单），软偏好多选或假设披露，琐事直接假设。这是「澄清需求」的核心交互逻辑。
- **校验与修复**：`_parse_proposal` 容错 markdown 围栏/截断；失败后 `_retry_proposal` 把校验错误回喂模型做一次校正；仍失败则降级为可读错误文本，绝不静默丢弃。

## 3. 关键交付物

| 组件 | 文件 | 职责 |
|---|---|---|
| 决策引擎 | `app/planning/runtime.py::PlanningDecisionEngine` | 组装提示词、调用 LLM、解析/校正提案、计量 token |
| 提案契约 | `app/planning/runtime.py::DecisionProposal` | `respond/ask_user/update_plan/request_approval` 四种 action |
| 编排校验 | `app/planning/runtime.py::InteractionOrchestrator` | 白名单 + 阶段 + 数量约束（M5 约束） |

| 决策提示词 | `runtime.py::_proposal_request`（内联） | 硬约束/软偏好/琐事分类 + 逐条规则 |

## 4. 验收标准逐条核查

| 验收项 | 结果 | 证据 |
|---|---|---|
| 简单问答不强制生成卡片 | 满足 | 提示词 `STEP 0` + `respond` 路径不创建 interaction |
| 适合的任务生成有效组件，结构通过 Schema | 满足 | `DecisionProposal.model_validate` 严格校验 |
| 无权限组件无法输出为可执行 UI | 满足 | `InteractionType` 白名单 + `InteractionOrchestrator.enforce` |
| 模型异常/JSON 不完整时降级为可读文本 | 满足 | `_load_proposal_json` 容错 + `_retry_proposal` 校正 + 失败返回错误文本 |
| 评测记录选择准确率、无效率、延迟、Token 成本 | **部分满足** | 评测集 `evals/ui_selection_cases.jsonl`（本轮新增 44 例）；跑分器未建 |

## 6. 差距与风险

- **跑分器未建**：需要一个调用 `PlanningDecisionEngine`（用 fake provider）的脚本，逐例比对 `action/component`，输出准确率/无效率/延迟/Token。属后续门禁项。
- **延迟与成本未实测**：`temperature=0` + `json_object` 已控制随机性，但端到端延迟与 token 成本需真实模型跑分。
- **风险**：模型偶发输出 `source="user"`（非法值）已在 `_parse_proposal` 归一化为 `assumed`；仍建议评测集覆盖此类异常输入。
